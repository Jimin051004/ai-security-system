# 13. 상용형 멀티 사이트 WAF 연결 설계

## 1. 문서 목적

이 문서는 현재 단일 `UPSTREAM_URL` 기반 WAF 프록시를 실제 서비스 연결 방식에 가까운 멀티 사이트 WAF 구조로 확장하기 위한 설계 문서이다.

현재 구조는 하나의 WAF 프록시가 하나의 원본 서버만 바라본다.

```text
브라우저 -> WAF 프록시(main.py:8081) -> UPSTREAM_URL -> Juice Shop
```

목표 구조는 여러 도메인과 여러 원본 서버를 대시보드에서 등록하고, 요청의 `Host` 헤더를 기준으로 각 사이트의 정책과 origin을 선택하는 방식이다.

```text
브라우저
  -> DNS / TLS / Caddy 또는 Nginx
  -> WAF Gateway
  -> Host 기반 사이트 식별
  -> 사이트별 WAF 정책 검사
  -> 사이트별 origin 전달
  -> 탐지/차단 이벤트 저장
  -> 대시보드 통계/정책 관리
```

## 2. 무료 범위 기준

| 번호 | 항목 | 무료 구현 가능 여부 | 설계 판단 |
|---|---|---:|---|
| 2-1 | 사이트 등록 | 가능 | SQLite 기반 `sites` 테이블과 대시보드 UI로 구현 |
| 2-2 | DNS 연결 | 조건부 가능 | 도메인이 이미 있으면 Cloudflare Free 또는 기존 DNS로 가능 |
| 2-3 | TLS 인증서 | 가능 | Let's Encrypt 또는 Caddy automatic HTTPS 사용 |
| 2-4 | 멀티 사이트 라우팅 | 가능 | `Host` 헤더 기반 origin 매핑 |
| 2-5 | 사이트별 정책 | 가능 | DB 기반 정책 저장 |
| 2-6 | 로그 저장 | 가능 | SQLite 확장으로 구현 |
| 2-7 | 인증/인가 | 가능 | 기존 `auth.py` 확장 |
| 2-8 | 관리자 알림 | 부분 가능 | 브라우저/대시보드 내부 알림 먼저 구현, 외부 SMS/카톡은 유료 가능성 있음 |
| 2-9 | 고가용성 | 제한적 | 무료 범위에서는 health check와 명확한 502 처리까지 구현 |

## 4. 현재 코드 기준 핵심 차이

| 번호 | 현재 코드 | 목표 구조 |
|---|---|---|
| 4-1 | `UPSTREAM_URL` 하나만 사용 | `Host` 별 origin을 DB에서 조회 |
| 4-2 | `SITE_ID`는 워커 라벨 중심 | `site_id`가 사이트 정책과 origin의 기본 키가 됨 |
| 4-3 | 대시보드는 로그/설정 중심 | 대시보드가 사이트 등록과 정책 관리까지 담당 |
| 4-4 | `traffic_events` 중심 로그 | `sites`, `site_policies`, `site_routes`, `waf_events` 구조로 확장 |
| 4-5 | TLS는 앱 외부 문제 | Caddy/Nginx 앞단 배치 가이드 포함 |
