# 13-2. 아키텍처 설계

## 1. 전체 목표

현재 단일 사이트 프록시를 다음 구조로 확장한다.

```text
Client Browser
  -> DNS
  -> TLS Front Proxy(Caddy 또는 Nginx)
  -> WAF Gateway(FastAPI main.py)
  -> Site Resolver
  -> WAF Policy Engine
  -> Origin Forwarder
  -> Origin Web Server

WAF Gateway
  -> Event Recorder
  -> SQLite
  -> Dashboard
```

## 2. 무료 범위 권장 배치

## 2-1. 로컬/졸업작품 시연 배치

```text
shop.local.test     -> 127.0.0.1:8081 -> Juice Shop A :3001
admin.local.test    -> 127.0.0.1:8081 -> Juice Shop B :3002
dashboard.local     -> 127.0.0.1:8090 -> dashboard_app.py
```

이 방식은 실제 DNS 비용 없이 `/etc/hosts` 또는 브라우저 Host 헤더 시뮬레이션으로 멀티 사이트 라우팅을 보여줄 수 있다.

## 2-2. 실제 도메인 배치

```text
shop.example.com
  DNS A/CNAME -> WAF 서버 공인 IP 또는 waf.example.com
  HTTPS -> Caddy
  HTTP proxy -> WAF Gateway :8081
  origin -> http://10.0.0.5:3000
```

도메인이 이미 있다면 DNS 비용은 추가로 들지 않는다. TLS 인증서는 Let's Encrypt 또는 Caddy automatic HTTPS를 사용한다.

## 3. 주요 컴포넌트

| 번호 | 컴포넌트 | 역할 | 예상 파일 |
|---|---|---|---|
| 3-1 | Dashboard Site Manager | 사이트 등록/수정/삭제 UI와 API | `dashboard_app.py`, `templates/dashboard/partials/sites.html` |
| 3-2 | Site Repository | `sites`, `site_policies`, `site_exceptions` 저장/조회 | `site_registry.py` 또는 `traffic_log.py` 확장 |
| 3-3 | Site Resolver | 요청 `Host`로 site와 origin 결정 | `site_resolver.py` |
| 3-4 | Policy Engine | 사이트별 detect/block/rule 설정 적용 | `waf_policy.py` |
| 3-5 | Origin Forwarder | 결정된 origin으로 요청 전달 | `proxy_forwarder.py` |
| 3-6 | Event Recorder | 요청/탐지/차단 이벤트 저장 | `traffic_log.py` 확장 |
| 3-7 | TLS Front Proxy Config | Caddy/Nginx 설정 예시 생성 | `docs` 또는 `scripts` |

## 4. 요청 처리 흐름

## 4-1. 정상 요청 흐름

```text
1. 사용자가 https://shop.example.com/products 접속
2. DNS가 WAF 서버로 연결
3. Caddy가 TLS 종료 후 WAF Gateway로 요청 전달
4. WAF Gateway가 Host=shop.example.com 확인
5. Site Resolver가 sites 테이블에서 site_id와 origin 조회
6. Policy Engine이 사이트 정책 조회
7. WAF가 요청 검사
8. 차단 대상이 아니면 origin으로 요청 전달
9. origin 응답을 사용자에게 반환
10. traffic/request 이벤트 저장
```

## 4-2. 차단 요청 흐름

```text
1. 공격성 요청 수신
2. Host 기반 사이트 식별
3. 요청 스냅샷 생성
4. OWASP 룰 검사
5. 필요 시 AI Second Pass 판단
6. block 모드이고 차단 조건 충족 시 403 차단 응답
7. detections/waf_events 저장
8. 대시보드 통계 갱신
```

## 4-3. 탐지 모드 흐름

```text
1. 공격성 요청 수신
2. WAF가 탐지 결과 생성
3. 사이트 정책이 detect이면 origin으로 요청은 통과
4. 이벤트에는 blocked=false, detected=true 저장
5. 대시보드에서는 "탐지만 됨"으로 표시
```

## 5. Host 기반 사이트 식별

## 5-1. 입력

| 입력 | 설명 |
|---|---|
| `Host` 헤더 | 사용자가 접근한 도메인 |
| `X-Forwarded-Host` | Caddy/Nginx 뒤에서 원래 Host를 전달할 때 사용 |
| `X-Forwarded-Proto` | 원래 scheme이 `https`인지 확인 |

## 5-2. 처리

```text
1. trusted proxy 환경이면 X-Forwarded-Host 우선
2. 아니면 Host 사용
3. 포트 제거 후 소문자 정규화
4. sites.domain과 비교
5. 없으면 404 Unknown Site 또는 기본 사이트 fallback
```

## 5-3. 출력

| 출력 | 설명 |
|---|---|
| `site_id` | 정책/로그 저장 기본 키 |
| `origin_url` | 요청을 전달할 원본 서버 |
| `mode` | `detect`, `block`, `disabled` |
| `ai_enabled` | AI Second Pass 사용 여부 |

## 6. TLS 처리 방식

## 6-1. 앱 내부 직접 TLS는 1차 구현에서 제외

FastAPI 앱이 직접 인증서를 발급/갱신하는 방식은 구현량과 운영 리스크가 크다.

## 6-2. 권장 방식

```text
Caddy :80/:443
  -> 자동 HTTPS
  -> reverse_proxy 127.0.0.1:8081

FastAPI WAF Gateway :8081
  -> HTTP 내부 통신
```

## 6-3. Caddyfile 예시

```caddyfile
shop.example.com {
    reverse_proxy 127.0.0.1:8081 {
        header_up Host {host}
        header_up X-Forwarded-Host {host}
        header_up X-Forwarded-Proto {scheme}
    }
}

admin.example.com {
    reverse_proxy 127.0.0.1:8081 {
        header_up Host {host}
        header_up X-Forwarded-Host {host}
        header_up X-Forwarded-Proto {scheme}
    }
}
```

## 7. DNS 연결 방식

## 7-1. A 레코드

```text
shop.example.com A 203.0.113.10
```

WAF 서버가 공인 IP를 가지고 있을 때 사용한다.

## 7-2. CNAME

```text
shop.example.com CNAME waf.example.net
```

WAF 서비스 대표 도메인이 있을 때 사용한다.

## 8. 기존 코드와의 연결

| 번호 | 기존 기능 | 확장 방식 |
|---|---|---|
| 8-1 | `UPSTREAM_BASE` | 사이트가 없을 때 fallback origin으로 유지 |
| 8-2 | `SITE_ID` | 단일 워커 모드 fallback으로 유지 |
| 8-3 | `_forward()` | `origin_url`을 인자로 받는 구조로 분리 |
| 8-4 | `_run_waf_gate()` | 사이트 정책을 인자로 받아 detect/block 처리 |
| 8-5 | `traffic_log.record_event_dict()` | site/domain/request/detection 필드 확장 |
| 8-6 | `/__waf/api/settings/waf-enabled` | 사이트별 `mode`와 룰 설정 API로 확장 |

## 9. 단계적 구현 전략

| 단계 | 목표 | 이유 |
|---|---|---|
| 9-1 | DB에 `sites`와 `site_policies` 추가 | origin과 정책을 코드 밖으로 분리 |
| 9-2 | 대시보드 사이트 관리 API 추가 | 사이트 등록/수정 흐름 확보 |
| 9-3 | Host 기반 Site Resolver 추가 | 멀티 도메인 라우팅 핵심 |
| 9-4 | 프록시 forwarder 분리 | `main.py` 복잡도 감소 |
| 9-5 | 정책 엔진 적용 | detect/block/disabled, AI 여부 반영 |
| 9-6 | 예외 경로/IP 정책 추가 | 실제 운영형 제어 기능 |
| 9-7 | Caddy/Nginx 설정 문서/생성 | 실제 도메인 연결 시연 |
