# 13-1. 요구사항 정리

## 1. 프롬프트 목적

현재 실습용 WAF 프로젝트를 실제 상용 서비스 연결 방식에 가깝게 확장한다.

핵심 목표는 사용자가 대시보드에서 보호할 사이트를 등록하고, DNS/TLS/프록시/WAF/로그/정책 관리 흐름을 하나의 서비스처럼 연결하는 것이다.

## 2. 명시된 요구사항

| 번호 | 요구사항 | 설명 |
|---|---|---|
| 2-1 | 사이트 등록 기능 | 보호할 도메인과 원본 서버 origin을 대시보드에서 등록 |
| 2-2 | DNS 연결 안내 | A 레코드 또는 CNAME을 WAF 쪽으로 연결하는 흐름 제공 |
| 2-3 | TLS 인증서 설정 | HTTPS 요청을 WAF가 먼저 받도록 TLS 구성 |
| 2-4 | 멀티 사이트 지원 | 여러 웹사이트를 등록하고 관리 |
| 2-5 | Host 기반 정책 결정 | 요청의 `Host` 헤더로 어떤 사이트 정책을 적용할지 결정 |
| 2-6 | 도메인 기반 라우팅 | `shop.example.com`과 `admin.example.com`을 서로 다른 origin으로 전달 |
| 2-7 | 사이트 관리 화면 | 사이트 추가, origin 수정, 차단/탐지 모드 선택 |
| 2-8 | 룰 ON/OFF | 사이트별 WAF 룰 활성/비활성 |
| 2-9 | 예외 경로 관리 | 특정 URL 경로에 대해 룰 예외 처리 |
| 2-10 | 로그 저장 구조 개선 | `sites`, `requests`, `detections`, `rules`, `users`, `audit_logs` 등 명확한 테이블 설계 |
| 2-11 | 인증/인가 강화 | 로그인 여부와 사이트 접근 권한 검증 |
| 2-12 | 운영 안정성 | WAF, origin, 로그 저장 실패 상황 처리 |
| 2-13 | WAF 요청 검사 | SQL Injection, XSS, SSRF, 파일 업로드 공격 등 검사 |
| 2-14 | AI Second Pass 연동 | 필요한 경우 AI 2차 판단 사용 |
| 2-15 | 정상 요청 origin 전달 | 차단되지 않은 요청은 실제 웹서버로 전달 |
| 2-16 | 탐지/차단 이벤트 전송 | 로그 저장, 통계 생성, 위험도 계산, 관리자 알림 |
| 2-17 | 대시보드 정책 조정 | 탐지 모드/차단 모드, 예외, IP 허용/차단, 룰 민감도 조정 |
| 2-18 | 무료 범위 구현 | 유료 SaaS 의존 없이 가능한 범위에서 구현 |

## 3. 암시된 요구사항

| 번호 | 요구사항 | 추론 근거 |
|---|---|---|
| 3-1 | 기존 Juice Shop 실습 유지 | 졸업작품 시연에서 기존 환경이 필요함 |
| 3-2 | 단일 origin 방식과 호환 | `UPSTREAM_URL` 기반 구조를 한 번에 제거하면 리스크가 큼 |
| 3-3 | SQLite 기반 1차 구현 | 현재 프로젝트가 SQLite를 사용하고 있어 무료/간단 구현에 적합 |
| 3-4 | 단계적 마이그레이션 | DB, 라우팅, 화면, 정책을 동시에 바꾸면 장애 원인 추적이 어려움 |
| 3-5 | 관리자/일반 사용자 권한 분리 | 사이트별 로그와 정책이 생기면 인가가 필수 |
| 3-6 | TLS는 앱 내부보다 앞단 프록시가 담당 | FastAPI에서 직접 인증서 자동화를 구현하는 것보다 Caddy/Nginx가 적합 |

## 4. 제약 조건

| 번호 | 제약 조건 | 설명 |
|---|---|---|
| 4-1 | 무료 범위 | 외부 유료 WAF, 유료 DB, 유료 알림 서비스는 1차 구현에서 제외 |
| 4-2 | 로컬 시연 가능 | 도메인 없이도 `Host` 헤더 또는 `/etc/hosts`로 시연 가능해야 함 |
| 4-3 | 기존 테스트 유지 | 현재 93개 테스트가 깨지지 않아야 함 |
| 4-4 | 기존 대시보드 유지 | UI/UX 프리뷰와 기존 로그 화면을 망가뜨리지 않아야 함 |
| 4-5 | 인증 우회 금지 | 일반 사용자가 다른 사이트 로그/정책을 볼 수 없어야 함 |
| 4-6 | SSRF 방어 필요 | origin URL을 사용자가 등록하므로 내부망 접근 제한이 필요 |

## 5. 필요한 입력값

| 번호 | 입력값 | 설명 |
|---|---|---|
| 5-1 | 사이트 이름 | 대시보드 표시용 이름 |
| 5-2 | 보호 도메인 | 예: `shop.example.com` |
| 5-3 | origin URL | 예: `http://127.0.0.1:3001` 또는 `https://origin.example.com` |
| 5-4 | 운영 모드 | `detect`, `block`, `disabled` |
| 5-5 | 룰 설정 | 룰별 활성 여부와 최소 심각도 |
| 5-6 | 예외 경로 | 예: `/health`, `/static/*` |
| 5-7 | IP 정책 | 허용/차단 IP 목록 |
| 5-8 | AI Second Pass 사용 여부 | 사이트별 AI 보조 판단 활성화 |

## 6. 기대 출력값

| 번호 | 출력값 | 설명 |
|---|---|---|
| 6-1 | 사이트 등록 결과 | site_id, domain, origin, 상태 |
| 6-2 | DNS 연결 안내 | A/CNAME 예시와 검증 상태 |
| 6-3 | TLS 구성 안내 | Caddyfile/Nginx 예시 또는 인증서 상태 |
| 6-4 | 사이트별 대시보드 | 해당 사이트의 요청/차단/통계 |
| 6-5 | 정책 적용 결과 | detect/block/disabled 반영 |
| 6-6 | 탐지/차단 이벤트 | 요청, 탐지 룰, 위험도, AI 판단 정보 |

## 7. 애매한 부분과 임시 가정

| 번호 | 애매한 부분 | 임시 가정 | 확인 필요 여부 |
|---|---|---|---|
| A1 | 실제 보유 도메인 여부 | 일단 로컬/사설 IP와 `/etc/hosts` 시연을 기본으로 설계 | 필요 |
| A2 | 운영 서버 배포 여부 | Mac 로컬 또는 같은 LAN 서버 기준으로 1차 구현 | 필요 |
| A3 | TLS 자동화 수준 | 1차는 Caddy 설정 파일 생성/가이드, 앱 내부 자동 발급은 보류 | 필요 |
| A4 | 관리자 알림 방식 | 무료 범위에서 대시보드 내부 알림과 로그 기반 알림부터 구현 | 필요 |
| A5 | DB 종류 | SQLite 유지, 추후 PostgreSQL 전환 가능하게 테이블 경계를 명확히 함 | 필요 |

## 8. 사용자에게 확인할 질문

| 번호 | 질문 | 필요한 이유 |
|---|---|---|
| Q1 | 실제 도메인을 가지고 있는가? | DNS/TLS 시연 방식 결정 |
| Q2 | 시연은 로컬 Mac, 같은 LAN, 또는 클라우드 VM 중 어디에서 할 것인가? | Caddy/TLS/DNS 연결 방식 결정 |
| Q3 | 1차 구현은 Juice Shop 2개 사이트로 멀티 사이트 시연해도 되는가? | 무료/안전한 검증 환경 구성 |
| Q4 | 사이트별 룰 ON/OFF는 전체 모듈 단위부터 시작해도 되는가? | 구현 범위 조절 |
