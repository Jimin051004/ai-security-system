## 2. 프로젝트를 만드는 목적

1. **교육·연구**: 상용 WAF에 의존하지 않고, **요청 단위 보안 점검 파이프라인**을 직접 구현·실험한다.
2. **재현 가능한 검증**: Juice Shop 등 표준 타깃 앞에 두고 **탐지·차단·로그**를 같은 시나리오로 반복 검증한다.
3. **확장성**: OWASP 항목별 모듈(`a01`~`a10`)과 **환경 변수 기반 정책**으로 기능을 단계적으로 늘릴 수 있게 한다.
4. **운영 가시성**: SQLite에 트래픽·탐지 내역을 남기고 **웹 대시보드**로 조회한다.
5. **인공지능 연계 준비**: 현재는 **규칙·패턴이 1차 점검**을 담당하고, 후반에 **로컬 LLM**으로 요약·보조 판단·자연어 설명을 얹을 수 있는 구조를 목표로 한다.

## 4. 프로그램 동작 방식

### 4.1 역할

- 브라우저(또는 공격 도구)는 **프록시 주소**(예: `http://127.0.0.1:8080`)만 본다.
- 프록시는 내부적으로 **`UPSTREAM_URL`**(예: `http://127.0.0.1:3001`)의 Juice Shop으로 동일 메서드·경로·쿼리·본문을 **전달**한다.
- **WAF가 켜져 있으면** 전달 전에 요청을 **스캔**하고, 정책에 따라 **403 차단** 또는 **통과**한다.

### 4.2 요청 → 점검 → 차단/통과 흐름

1. **요청 수신** (`main.py`): 클라이언트 HTTP 요청 진입.
2. **컨텍스트 생성** (`request_snapshot.request_to_context`): 메서드, 경로, 쿼리스트링, 헤더, 본문 앞부분(`body_preview`, 길이 상한 설정 가능)을 `RequestContext`로 묶는다.
3. **모듈 순차 스캔** (`detector.scan_request`): `owasp.MODULES`에 등록된 **A01~A10** 각 모듈의 `scan(ctx)`를 호출한다.
4. **탐지 결과 집계**: 각 모듈이 `Finding`(규칙 ID, 심각도, 증거 문자열, 위치 등) 목록을 반환한다.
5. **차단 여부** (`detector.waf_blocking_findings`): 환경 변수 **`WAF_BLOCK_MIN_SEVERITY`** 이상인 탐지가 있으면 차단 후보. **A05(인젝션)** 는 규칙 ID가 `A05-`로 시작하면 **심각도와 무관하게** 차단 대상에 포함되는 정책이 있다.
6. **차단 시**: HTML(`waf_blocked.html`) 또는 JSON 403. 탐지 요약은 대시보드·DB 기록에 쓸 수 있는 형태로 남긴다.
7. **통과 시**: `httpx`로 업스트림에 요청을 보내고, 응답 헤더·본문을 가공해 클라이언트에 반환한다.
  - LAN 접속 시 HTML/JS에 박힌 `http://127.0.0.1:3001` 같은 절대 URL을 **클라이언트가 접속한 호스트**(예: `192.168.x.x:8080`)로 **치환**하는 로직이 있다.
8. **기록** (`traffic_log`): 통과/차단 여부와 메타데이터·탐지 JSON을 SQLite에 적재한다.
9. **운영 UI**: `/__waf/dashboard` 등 **프록시 전용 경로**로 대시보드·요약 API를 제공한다 (업스트림과 경로 충돌 방지).

### 4.3 구조도 (텍스트)

```
[클라이언트] → [FastAPI 프록시 :8080]
                    → WAF 스캔(detector + owasp/a01~a10)
                    → 차단? → 403 + 로그
                    → 통과? → httpx → [UPSTREAM_URL : Juice Shop :3001]
                    → 응답 rewrite → 클라이언트
                    ↓
              [SQLite] ← 트래픽·탐지 이벤트
              [/__waf/*] ← 대시보드·API
```

| 모듈 | 파일 | 구현 상태 | 탐지에 사용하는 방법(요약) |
|------|------|-----------|---------------------------|
| **A01** | `owasp/a01.py` | 미완성 | (현재 탐지 없음) **계획:** 민감 경로·메서드 **매트릭스**, 리소스 ID **열거 휴리스틱**, IP 기준 **슬라이딩 윈도우 카운터**, 쿼리·JSON 키 패턴, **정규식** |
| **A02** | `owasp/a02.py` | 미완성 | (현재 탐지 없음) **계획:** 디버그·설정 노출 **경로 블록리스트**(정규식·정적 리스트), GraphQL `__schema` 등 **쿼리 문자열 패턴**, 프록시 혼동 유발 **헤더 이름·값 패턴** |
| **A03** | `owasp/a03.py` | 미완성 | (현재 탐지 없음) **계획:** `package.json`, lockfile 등 **경로·파일명 패턴**(정규식), 경로 탐색(`../`) 결합은 A06과 연계 가능 |
| **A04** | `owasp/a04.py` | 미완성 | (현재 탐지 없음) **계획:** 쿼리스트링 **파라미터 이름 패턴**, 본문 JSON **필드 길이·형식(정규식)**, 민감 값은 evidence **마스킹** |
| **A05** | `owasp/a05.py` | 규칙 구현 | **정규식(re)** 다중 룰(SQL·XSS·CMD·LDAP·XPath·EL·SSTI·CRLF 등), 검사 대상 **문자열 수집** 후 스캔(경로·쿼리·`body_preview`·선별 헤더), 쿼리/폼은 **URL 디코딩** 후 매칭, 위치별 **오탐 완화(prefix 스킵)**, **rule_id 기준 중복 제거** |
| **A06** | `owasp/a06.py` | 규칙 다수 | **JSON 파싱(`json.loads`)** 후 키·값 조건 검사, 실패 시 **정규식 폴백**, **`urllib.parse.parse_qs`**로 쿼리 파라미터 검사, **경로+HTTP 메서드 정규식 룰**, **IP·경로별 인메모리 레이트 리밋(시계열 카운터)**, 디렉터리 탐색·dot 경로 **패턴**, 일부 **Shannon 엔트로피 → 가산 점수 → 심각도** |
| **A07** | `owasp/a07.py` | 미완성 | (현재 탐지 없음) **계획:** 로그인 등 **엔드포인트별 레이트 리밋**, 세션 ID in URL **정규식**, `Authorization: Basic` **디코드·패턴**, OAuth 바디 휴리스틱 |
| **A08** | `owasp/a08.py` | 미완성 | (현재 탐지 없음) **계획:** 서명·checksum 관련 **키·값 휴리스틱**, 역직렬화 **바이너리 시그니처**(hex/base64), 알려진 **위험 엔드포인트 경로 리스트** |
| **A09** | `owasp/a09.py` | 미완성 | (현재 탐지 없음) **계획:** 단일 요청만으로는 한계 — **환경 변수·설정 자가진단**, 민감 요청에 **상관 ID 헤더 존재 여부**, (모듈 외) **SQLite 집계·배치 리포트** |
| **A10** | `owasp/a10.py` | 규칙 구현 | **정규식 룰** + 경로·쿼리·본문·헤더 구간별 적용, URL **디코딩**, 쿼리 **`parse_qsl`**, 본문 **JSON 구조 분석**(중첩 깊이·`__proto__` 등), 일부 값에 **Shannon 엔트로피 가산** 후 점수→심각도, **rule_id 중복 제거** |

#### 구현된 모듈만 조금 더 구체적으로 (A05 / A06 / A10)

- **A05 Injection**  
  - **핵심:** 위험 문자열을 잡는 **컴파일된 정규식 패턴**을 카테고리별로 많이 둔다.  
  - **입력 전처리:** 쿼리·폼 값은 디코딩해 인코딩 우회를 줄인 뒤 매칭한다.  
  - **출력:** 매칭된 룰마다 `Finding`(규칙 ID, 심각도, 증거 발췌, 위치 라벨).

- **A06 Insecure Design**  
  - **핵심:** JSON이면 **파싱 후 의미 있는 키·값**(가격·역할·대량할당 등)을 검사하고, 파싱 실패 시에만 문자열 **정규식**으로 같은 신호를 찾는다.  
  - **추가:** “어떤 URL을 어떤 메서드로 호출했는지”는 **경로 정규식 + 메서드 집합**으로 본다.  
  - **동일 IP 과다 요청**은 시간 윈도우 안의 요청 **횟수 카운터**로 본다.

- **A10 Exceptional Conditions**  
  - **핵심:** `undefined`·경계값·`__proto__`·깊은 JSON·NoSQL 연산자 형태 등 **비정상 입력**을 정규식과 구조 검사로 나눠 잡는다.  
  - **가변 심각도:** 문자열 **엔트로피**가 높으면 점수를 올려 심각도를 매긴다.

미완성 모듈의 세부 계획은 아래 **§6.4** 표와 맞추면 된다.

### 4.5 프로젝트 진행 — 기술적 특징 (발표 슬라이드형 요약)

아래는 **“프로젝트 진행 과정 / 기술적 특징”** 슬라이드를 만들 때 쓰기 좋게, 핵심만 블록으로 묶은 설명이다. (§4.4의 모듈별 표와 **같은 시스템**을 다른 말로 정리한 것이다.)

---

#### 1) 다층 분석 엔진

- **정규식·패턴 계층:** URL 경로·쿼리·본문 미리보기·선별 헤더에 대해 **카테고리별 시그니처**를 적용 (A05 인젝션 등).
- **구조 기반 분석 계층:** JSON은 **`json.loads` 후 키·값·중첩 깊이** 등을 검사하고, 실패 시 **문자열 정규식**으로 폴백 (A06·A10).
- **행위·설계 계층:** HTTP 메서드 + 경로 **매트릭스**, 관리·워크플로우성 URL, **IP·경로별 요청 빈도(시계열)** 로 비즈니스 로직·설계 취약 신호를 본다 (A06 등).
- *범위 한계:* 업스트림 **애플리케이션 소스코드 전체를 AST로 분석**하거나, 언어별 정적 분석기를 두는 구조는 **아니다**. 분석 대상은 **HTTP 요청 스냅샷**이다.

---

#### 2) 신뢰도·점수(심각도) 체계

- **엔트로피 활용:** 일부 룰에서 문자열 **Shannon 엔트로피**가 높을수록 **가산 점수**를 주어 난독화·무작위 페이로드에 가중 (A06·A10 등).
- **다중 가중:** 규칙마다 **base_score**를 두고, 엔트로피·과다 요청 비율 등과 **조합**해 최종 심각도(LOW~CRITICAL)로 매핑한다.
- **정책 연동:** 환경 변수 **`WAF_BLOCK_MIN_SEVERITY`** 로 “어디까지 차단할지”를 조정하고, A05 인젝션은 **규칙 접두어(`A05-`)별 추가 정책**으로 차단 범위를 정한다.

---

#### 3) 오탐(거짓 양성) 완화

- **맥락·위치 인지:** 같은 패턴도 **어느 필드에서 왔는지**(Referer vs body 등)에 따라 룰 적용을 **건너뛰는** 옵션 (`skip_location_prefixes` 등).
- **정규화 후 매칭:** 쿼리·폼 값은 **URL 디코딩** 후 매칭해 인코딩 우회를 줄인다.
- **차단 임계:** 낮은 심각도는 **로그·관찰**에 두고, 높은 심각도만 차단하도록 **임계값**으로 조절한다.

---

#### 4) 의존성·공급망 관련 신호 (로드맵)

- **현재:** 프록시는 주로 **HTTP 요청**만 본다. **CVE DB와 버전 자동 대조**까지는 구현 범위에 포함하지 않는다.
- **계획(A03 등):** `package.json`, lockfile 등 **의존성 정의 파일에 대한 직접 요청(경로 패턴)** 을 탐지해, **정보 유출·정찰성 접근** 신호로 쓴다. (진짜 취약 버전 판별은 SBOM·CI 파이프라인이 담당.)

---

#### 5) 패턴·룰 운영 체계

- **모듈·규칙 ID:** OWASP Top 10:2025 항목별 **`owasp/a01`~`a10`** 파일과 **`A05-SQL-001`** 같은 **고정 규칙 ID**로 관리한다.
- **설정 기반 정책:** `UPSTREAM_URL`, `WAF_ENABLED`, `WAF_BODY_PREVIEW_MAX` 등 **환경 변수**로 동작을 바꾼다.
- **검증·확장:** Juice Shop 시나리오와 맞춘 **페이로드·pytest**로 회귀 검증을 늘려 간다.
- **성능:** 본문은 **`body_preview` 상한**으로 길이를 제한해 실시간 프록시 경로의 부담을 줄인다.

## 5. AI를 사용하는 이유 — 기존 탐지 시스템과의 비교

### 5.1 기존(전통적) 탐지에 가까운 현재 구현


| 특징         | 설명                                                           |
| ---------- | ------------------------------------------------------------ |
| 시그니처·규칙 기반 | 알려진 패턴(인젝션 문자열, 비정상 경로 등)을 **빠르게** 매칭. 오탐·미탐은 **패턴 품질**에 좌우. |
| 설명 가능성     | 규칙 ID·위치·증거 문자열로 **왜 막았는지**를 기계적으로 남기기 좋다.                   |
| 지연·비용      | 로컬 연산 위주라 **실시간 프록시 경로**에 두기 적합.                             |


→ 본 프로젝트의 **1차 취약점 점검**은 이 방식(A05·A10 등)으로 구현되어 있다.

### 5.2 AI(특히 LLM)를 **추가**하려는 이유


| 비교 축       | 전통적 규칙/시그니처                   | AI(생성형·분류 모델) 보조                             |
| ---------- | ----------------------------- | -------------------------------------------- |
| **미지의 변형** | 인코딩·난독화·문맥 의존 공격은 룰만으로 빠지기 쉬움 | 문맥·패러프레이즈에 강한 **보조 판단** 가능 (단, 비용·지연·환각 리스크) |
| **운영자 경험** | 로그가 길고 전문적                    | **한국어 요약**, 권장 조치, 유사 사례 안내                  |
| **오탐 처리**  | 임계값·화이트리스트 조정                 | “정상 업무로 보이는 입력”에 대한 **2차 완화 검토**(선택)         |
| **감사·교육**  | 규칙 나열                         | 자연어 **설명 생성**으로 교육 자료·리포트 초안                 |


### 5.3 본 프로젝트에서 권장하는 역할 분리

- **차단의 최종 결정**: 계속 **규칙 + 심각도 정책**이 주도 (예측 가능·감사 용이).
- **AI**: (1) 대시보드·배치에서의 **로그 요약**, (2) 애매 구간 **보조 스코어**, (3) **개발자용 설명 문구** 생성 등 **비차단 경로 또는 옵션**으로 도입.

이렇게 하면 “AI 보안 시스템”이라는 명칭과 **실제 안전한 운영 모델**이 맞는다.

## 6. 모듈별 탐지 방식 및 AI 활용(계획)

**모듈별 “어떤 기법으로 탐지하는지” 한눈에 보기:** **§4.4** 표 · 발표용 블록 요약은 **§4.5**.

**전제:** 지금 구현의 **1차 탐지**는 전부 **결정적 규칙**(정규식·파싱·경로 매칭·카운터 등)이다. **AI(LLM)** 는 아래 표의 **「AI 활용」** 처럼 **요약·설명·보조 판단·RAG**에 두는 것을 원칙으로 한다 (차단 최종권은 규칙·정책).

### 6.1 공통 (모든 모듈에 걸쳐)


| 구분            | 내용                                                                                                                |

### 6.3 AI를 요청 경로에 넣을 때(선택) 주의

- **지연·비용·환각**: 모든 요청마다 LLM 호출은 비현실적 → **차단 후**, 또는 **특정 심각도·샘플링**만.
- **프라이버시**: `body_preview`·Cookie를 외부 API로 보내지 말고, **로컬 LLM** + **마스킹** 원칙을 문서화.
- **감사**: “차단 이유”는 **규칙 ID**를 SSOT로 남기고, LLM 출력은 **부가 설명**으로만 표시.

### 6.4 계획 구현 방식 — 아직 구현 안 된 모듈 (A01·A02·A03·A04·A07·A08·A09)

**공통 구현 원칙**

- 입력은 기존과 동일하게 **`RequestContext`만** 사용 (경로·쿼리·헤더·`body_preview`). **응답 본문·세션 서버 상태**는 프록시가 기본적으로 보지 않으므로, 아래 “계획”은 **요청에서 보이는 신호** 위주다.
- A05/A06/A10과 동일하게 `Finding`(rule_id, severity, evidence, location) 형태로 반환, 필요 시 **인메모리 카운터·윈도우**(IP+경로)는 `a06` 레이트 패턴을 재사용하거나 `traffic_log` 집계를 후속 단계로 연계.
- Juice Shop 매핑은 `docs/OWASP_TOP10_2025_PDF_정리.md` 챌린지 이름과 맞춰 **검증 페이로드**를 `verification/`에 추가하는 것을 전제로 한다.

| **프록시 관점 메타 탐지** | 단일 요청만으로 “서버가 로그를 안 남김”은 불가. 대신 **(1)** 다른 모듈에서 이미 HIGH 이상 탐지된 요청인데 **대시보드 알림 규칙이 꺼져 있음** 같은 **설정 자가진단**(환경 변수 읽기) **(2)** 선택적 **상관 ID 강제**: `X-Request-ID`/`X-Correlation-ID` 없는 민감 `POST`를 LOW로 표기(기업 모드 옵션). |
| **배치·대시보드**      | 일별로 “차단됐으나 동일 IP 후속 활동 N건” 등 **알림 공백**을 SQLite 집계로 표시(모듈 `scan` 밖 **리포트 스크립트**도 후보).                                                                                                                            |


**역할:** 런타임 차단보다 **운영 성숙도·가시성** 지표에 가깝게 설계.

### 7.1 OWASP 모듈 (코드 기준)

**대시보드 API 표기** (`/__waf/api/modules`의 `implementation`): 현재 코드상 **`a05`, `a10`만 `rules`**, 나머지는 API 값 `skeleton`(의미: **미완성**)으로 노출된다. (A06은 구현 코드가 있으나 이 라벨 집합에는 미포함일 수 있음 — 발표 시 “코드와 대시보드 라벨을 맞출 예정”이라고 말할 수 있다.)

### 7.2 프록시·WAF·운영 기능 (구현됨)

- 리버스 프록시, 업스트림 헬스, 응답 URL rewrite, WAF on/off, 차단 최소 심각도 설정.
- 차단 페이지 HTML / JSON 분기.
- SQLite 트래픽 로그, 웹 대시보드(개요·로그·설정·SQL 읽기 전용 콘솔 등).
- `verification/` pytest 시나리오(대시보드, 차단, 프록시 rewrite, A05 일부 등).

### 7.3 아직 약하거나 없는 부분

- **LLM 연동**: 설계·문서 수준; **런타임에 모델 호출하는 코드는 핵심 파이프라인에 미포함**으로 보면 발표와 일치한다.
- **HTTPS 종단**: 일반적으로 별도 리버스 프록시(nginx 등) 또는 향후 과제로 설명.
- **A01~A04, A07~A09**: 규칙 채우기·Juice Shop 시나리오 매핑이 **후반 작업** — 구체 설계는 **§6.4** 참고.

## 8. 앞으로 추가할 모듈·기능 (로드맵)

- (선택) Prometheus 메트릭, 알림 웹훅.
