## 슬라이드 2 — 왜 이 프로젝트인가? (보안 + 인공지능)

- 웹 서비스는 **악성·비정상 요청**(인젝션, 설계 결함 유발 입력 등)에 지속 노출됨  
- **취약점 점검**을 “주기적 스캔”만이 아니라 **트래픽 경로에서 반복 검사**하는 측면으로 보면, **자동화·지능형 보조**가 의미 있음  
- 상용 WAF·점검 도구는 비용·폐쇄성 → **오픈소스 스택**으로 **교육·실험·재현 가능한** 시스템 구축  
- **OWASP Juice Shop** 등 의도적 취약 앱 앞에 두고 **탐지·차단·로그**로 **점검 결과를 검증**

**발표자 노트:** “AI로 모든 것을 대체”가 아니라 **점검 파이프라인에 AI를 어디에 둘지**가 졸업작품의 **연구 포인트**라고 말하면 됩니다.

## 슬라이드 3 — 프로젝트 한 줄 정의 (인공지능 기반 점검)

**인공지능 기반**이라는 표현의 뜻 (중간 발표 기준):


| 층           | 역할                                                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **현재(구현됨)** | 요청 컨텍스트를 OWASP Top 10:2025 **모듈별로 스캔**하는 **지능형 점검 파이프라인**(규칙·패턴·스코어링). 결과는 **심각도·근거(evidence)** 로 구조화되어 **차단·로그·대시보드**로 이어짐. |
| **후반(계획)**  | **로컬/오픈소스 LLM**으로 **애매한 요약**, **운영자용 한국어 설명**, **2차 의견(보조 판단)** 등 — **최종 차단 정책은 규칙과 설정**에 두는 방향 권장.                          |


**기술 스택 한 줄:** FastAPI **리버스 프록시 WAF** + SQLite 영속 로그 + 웹 대시보드.


| 구분        | 내용                                 |
| --------- | ---------------------------------- |
| 런타임       | Python, Uvicorn                    |
| 업스트림(테스트) | OWASP Juice Shop (Docker, 기본 3001) |
| 프록시 진입    | 예: 8080 → 점검(스캔) 후 업스트림으로 전달       |


**발표자 노트:** 제목의 **“인공지능 기반”**은 **(1) 자동화된 다단계 점검 파이프라인** + **(2) 향후 LLM 보조**를 묶은 브랜딩으로 설명하면 질문에 잘 대응됩니다.

## 슬라이드 4 — 전체 구조 (아키텍처)

```
[브라우저/공격자] → [프록시 + 취약점 점검 엔진 :8080] → [Juice Shop :3001]
                          ↓
                   SQLite 로그 · 웹 대시보드 /__waf/*
```

- **모든 요청**이 프록시를 통과할 때 **OWASP 모듈**이 순차 **점검(스캔)**  
- **차단** 시 HTML 차단 페이지 또는 JSON 403  
- **통과** 시 업스트림 응답을 클라이언트에 반환  
- 축적된 이벤트는 **분석·시각화·(향후) LLM 입력**으로 활용 가능한 형태(JSON 스냅샷)

**발표자 노트:** “리버스 프록시” = 클라이언트는 프록시 주소만 알고, 뒤에 실제 앱이 있다는 점만 짚으면 됩니다.

## 슬라이드 5 — 진행 현황: OWASP 모듈 (중간 시점)

대시보드 API(`/__waf/api/modules`) 기준 **구현도 라벨**과 맞춘 **현재 상태**입니다.


| 항목                 | OWASP ID                               | 코드 모듈                     | 중간 발표 시 설명                                                                |
| ------------------ | -------------------------------------- | ------------------------- | ------------------------------------------------------------------------- |
| **규칙 기반 점검 완료 수준** | **A05 Injection**                      | `owasp/a05.py`            | 다수 패턴·JSON 정밀 탐지 등 **실사용 가능한 룰**                                          |
| **규칙 기반 점검 완료 수준** | **A10 예외·조건 오류**                       | `owasp/a10.py`            | **실사용 가능한 룰**                                                             |

**한 줄 요약:** “**인젝션(A05)과 10번(A10) 모듈까지는 규칙 기반 취약점 점검이 동작**하고, 나머지는 **같은 인터페이스로 확장할 수 있게** 뼈대를 잡은 단계.”

**발표자 노트:** 심사위원이 “왜 AI인가?”라고 하면 **“점검 결과를 구조화하고, 후반에 LLM이 이 로그·컨텍스트를 읽어 보조한다”**로 연결합니다.

## 슬라이드 6 — 핵심 기능 ① 점검 엔진 (탐지·차단)

- **OWASP Top 10 : 2025** 항목별 모듈 (`owasp/a01` ~ `a10`)  
- `detector.py`가 **경로, 쿼리, 헤더, 본문 일부(`body_preview`)** 등을 `RequestContext`로 넘겨 **순차 스캔**  
- **심각도**에 따라 차단 여부 결정 (`WAF_BLOCK_MIN_SEVERITY` 등 환경 설정)  
- **완성도 높은 규칙**: 현재 **A05·A10** — 나머지는 **동일 파이프라인에 태우되 룰 채우기가 남음**

**발표자 노트:** “모든 항목 완성”이 아니라 **“점검 파이프라인과 우선순위 항목은 동작한다”**가 중간발표 메시지입니다.

## 슬라이드 7 — 핵심 기능 ② 웹 대시보드 (운영·분석 UI)

- URL: `**/__waf/dashboard`** (사이드 메뉴로 **페이지 분리**)  
- **개요**: 업스트림 상태, WAF on/off, 차단 KPI, 환경 요약  
- **탐지·차단 상세** / **프록시 로그** / **접속자(고유 IP)**  
- **저장소·DB 설정**: SQLite 경로, 스냅샷 한도, 전체 로그 초기화  
- **SQL 콘솔**: 테이블·컬럼 조회 + **읽기 전용** 쿼리(SELECT 등)  
- **(향후)** 대시보드에서 **“이벤트 요약(LLM)”** 버튼 등으로 **인공지능 레이어** 연결 여지

**발표자 노트:** 로그가 **SQLite에 영구 저장**되므로, 후반 **LLM·분석**의 **입력 데이터**로 쓰기 좋다고 말할 수 있습니다.

## 슬라이드 8 — 데이터·기록 (SQLite) — AI 연계의 기반

- 테이블 `**traffic_events`**: 시각, IP, 메서드, 경로, 상태코드, 차단 여부, 차단 시 **탐지 상세 JSON**  
- 기본 파일: 프로젝트 기준 `**waf_traffic.sqlite3`** (환경 변수 `TRAFFIC_LOG_DB`로 변경 가능)  
- 대시보드 API: 요약, 통계, 트래픽 스냅샷, 클라이언트 집계 등  
- **인공지능 관점:** 정형화된 **이벤트 스트림** = 나중에 **이상 탐지·요약·RAG**의 **근거 데이터**

**발표자 노트:** “데이터가 쌓이는 시스템”이 **AI 기반 점검·운영**으로 진화하기 쉽다는 점을 강조합니다.

## 슬라이드 11 — 데모 시나리오 (2분 안팎)

1. Docker로 **Juice Shop** 기동 (`docker compose -f docker-compose.yml up -d`)
2. **Uvicorn**으로 프록시 기동 (`--port 8080` 등)
3. 브라우저에서 `**http://127.0.0.1:8080`** → Juice Shop이 프록시 경유로 보임
4. **A05/A10에 걸리는 입력**(인젝션·예외 관련 페이로드 등) → **403 차단 페이지**
5. `**/__waf/dashboard`** → 로그·탐지 상세·SQL 콘솔에서 **같은 기록** 확인

**발표자 노트:** 현장 네트워크가 불안하면 **미리 녹화한 짧은 영상** 또는 **캡처 슬라이드**로 대체하세요.

## 슬라이드 13 — AI 활용 방향 (로컬 LLM·에이전트) — 상세

- **탐지 보조(2차 의견)**  
규칙으로 1차 판정한 뒤, 애매한 구간만 요청 맥락·로그를 보고 「악성 / 정상 / 불확실」 **보조 판단**. **최종 차단은 정책(규칙+임계값)** 에 두기 쉽습니다.
- **대응·설명(리미디에이션)**  
차단·고위험 시 **한국어 설명**, **수정 방향 힌트** 생성. **정책**과 **설명 생성**을 분리하면 구현·감사가 쉽습니다.
- **기록·운영(로그·대시보드)**  
트래픽 **요약**, 타임라인 설명, 이상 징후 나열은 **요청 경로 밖**(배치·버튼 클릭)에 두면 **지연·안정성** 이슈가 적습니다.
- **장기·선택**  
유사 사고 패턴 검색, 팀 가이드와 연결한 **RAG형 Q&A**

**발표자 노트:** 한 줄로 **「점검·차단은 규칙이 주도, AI는 요약·보조·사람이 읽는 설명」** 입니다.

## 다음에 이 MD·PPT에 보완하면 좋은 내용 (체크리스트)

발표 전에 아래를 채우면 **“인공지능 기반 취약점 점검”** 서사가 더 단단해집니다.

1. **시스템 구성도(한 장)**
  프록시 · 점검 엔진 · SQLite · 대시보드 · (점선) LLM 박스 — **데이터 흐름 화살표** 포함.
2. **A05 / A10 대표 페이로드 2~3개씩**
  슬라이드 또는 부록에 **탐지 규칙 ID + 짧은 예시** (데모 스크립트와 동일하게).
3. **중간 시점 성과 수치(있다면)**
  테스트 통과 개수, 샘플 요청 N건 중 차단 M건 등 **한 줄이라도 숫자**.
4. **LLM 연동 계획 1페이지**
  사용 모델(로컬 예: Llama 계열 등), 호출 위치(동기/비동기), **개인정보·로그 마스킹** 원칙.
