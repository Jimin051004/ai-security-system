# 10-2. 기능 설계

## 1. 기능 목적

AI 2차 탐지는 기존 정규식/구조 기반 WAF가 놓칠 수 있는 애매한 공격 변형을 로컬 LLM으로 재판단하고, 운영자가 이해할 수 있는 설명과 함께 차단 또는 관찰 상태로 남기는 기능이다.

## 2. 전체 흐름

```text
1. 요청 수신
2. RequestContext 생성
3. 기존 OWASP 룰 스캔
4. 기존 룰 차단 후보 확인
5. 기존 룰로 차단되면 즉시 차단
6. 차단 후보가 없고 AI 실행 조건을 만족하면 AI 2차 판단
7. AI 응답 JSON 검증
8. confidence와 recommended_action 확인
9. 기준 이상이면 AI-SECOND-PASS로 차단
10. 기준 미만/실패/비활성화면 기존 정책대로 통과
11. 상태와 이벤트를 로그/대시보드에 표시
```

## 3. 세부 기능 목록

| 번호 | 기능 | 설명 |
|---|---|---|
| 3-1 | AI 실행 조건 판단 | `AI_SECOND_PASS_ENABLED`, mode, 기존 finding, 의심 패턴으로 호출 여부 결정 |
| 3-2 | 안전한 입력 생성 | 민감 헤더/필드 마스킹 후 모델 입력 JSON 생성 |
| 3-3 | 프롬프트 생성 | JSON-only 응답을 요구하고 약한 근거는 allow하도록 지시 |
| 3-4 | Ollama 호출 | timeout, model, base URL 설정을 반영해 로컬 모델 호출 |
| 3-5 | 응답 파싱 | markdown 포함 응답도 JSON 객체만 추출해 검증 |
| 3-6 | 판단 정규화 | confidence 범위, severity, recommended_action 값을 안전한 값으로 정규화 |
| 3-7 | 차단 연동 | 기준 이상 악성 판단을 `AI-SECOND-PASS` Finding으로 변환 |
| 3-8 | 상태 추적 | 최근 AI 호출 성공/실패, 지연시간, 오류 유형을 메모리에 보관 |
| 3-9 | 상태 API | `/__proxy/health` 또는 별도 API에서 AI 상태 제공 |
| 3-10 | 대시보드 표시 | AI 사용 여부, 모델 상태, AI 차단 이벤트를 표시 |

## 4. 입력 데이터

| 번호 | 입력 | 처리 |
|---|---|---|
| 4-1 | `ctx.method` | 그대로 전달 |
| 4-2 | `ctx.path` | 길이 제한 후 전달 |
| 4-3 | `ctx.query_string` | 민감 키 마스킹, 길이 제한 |
| 4-4 | `ctx.headers` | allowlist 헤더만 전달, 민감 헤더 마스킹 |
| 4-5 | `ctx.body_preview` | 민감 필드 마스킹, 길이 제한 |
| 4-6 | 기존 `findings` | 최대 개수 제한, evidence 마스킹 |

## 5. 출력 데이터

| 번호 | 출력 | 설명 |
|---|---|---|
| 5-1 | `AISecondPassVerdict` | 모델 판단을 정규화한 내부 객체 |
| 5-2 | `Finding` | WAF 차단/표시와 호환되는 탐지 객체 |
| 5-3 | 상태 snapshot | 대시보드/health에서 확인할 운영 상태 |

## 6. 예외 상황

| 번호 | 예외 | 처리 |
|---|---|---|
| 6-1 | Ollama 미실행 | `None` 반환, 기존 룰 정책 유지, 상태에 오류 기록 |
| 6-2 | timeout | `None` 반환, 지연시간/timeout 기록 |
| 6-3 | 비JSON 응답 | 파싱 실패로 처리하고 차단하지 않음 |
| 6-4 | confidence 누락 | 0.0으로 처리 |
| 6-5 | severity 비정상 | HIGH 또는 NONE 등 보수적 기본값으로 정규화 |
| 6-6 | prompt injection 포함 | 모델 지시보다 시스템 프롬프트 우선, 응답 스키마 검증으로 제한 |

## 8. 구현 난이도

| 번호 | 영역 | 난이도 | 이유 |
|---|---|---|---|
| 8-1 | AI 호출/파싱 | 중 | 이미 구현되어 있으나 상태 추적과 실패 케이스 보강 필요 |
| 8-2 | 대시보드 연동 | 중 | 기존 UI 구조에 카드/필터 추가 필요 |
| 8-3 | 보안 마스킹 | 중상 | 누락된 민감정보 패턴이 있으면 보안 프로젝트 신뢰도에 영향 |
| 8-4 | 테스트 | 중 | 모델 없이 mock 기반으로 검증해야 함 |
