# 10-1. 요구사항 정리

## 1. 기능 목적

룰 기반 WAF가 명확히 차단하지 못한 애매한 요청을 로컬 AI 모델로 한 번 더 판단하고, 그 판단 결과를 차단, 로그, 대시보드, 발표 자료에서 설명 가능한 형태로 남긴다.

## 2. 명시된 요구사항

| 번호 | 요구사항 | 설명 |
|---|---|---|
| 2-1 | AI 2차 기능 완전구현 | 기존 골격 수준을 넘어 데모와 발표에 사용할 수 있는 완성 기능으로 만든다. |
| 2-2 | 기존 WAF와 연동 | A05/A06/A10 등 기존 룰 탐지 후 차단 후보가 없을 때 AI 2차 판단을 수행한다. |
| 2-3 | 로컬 AI 사용 | 외부 API가 아니라 Ollama 같은 로컬 모델 사용을 기본으로 한다. |
| 2-4 | 차단 가능 | AI가 악성으로 판단하고 신뢰도가 기준 이상이면 `AI-SECOND-PASS`로 차단한다. |

## 3. 암시된 요구사항

| 번호 | 요구사항 | 추론 근거 |
|---|---|---|
| 3-1 | 실패해도 프록시가 멈추지 않음 | WAF 요청 경로에 AI가 들어가므로 모델 장애가 전체 장애로 번지면 안 된다. |
| 3-2 | 민감정보 마스킹 | 요청 본문, Cookie, Authorization 등이 AI 프롬프트로 전달될 수 있다. |
| 3-3 | 상태 확인 기능 | 데모 중 AI가 켜져 있는지, 모델 연결이 되는지 확인해야 한다. |
| 3-4 | 대시보드 표시 | 졸업작품 시연에서 AI가 언제 판단했는지 보여줄 수 있어야 한다. |
| 3-5 | 테스트 가능성 | 로컬 모델이 없어도 mock으로 기능을 검증할 수 있어야 한다. |

## 4. 제약 조건

| 번호 | 제약 조건 | 설명 |
|---|---|---|
| 4-1 | 요청 지연 최소화 | 모든 요청마다 AI를 호출하면 프록시 성능이 급격히 떨어진다. |
| 4-2 | 차단 최종권 제한 | AI 판단은 보조 판단이며, 약한 근거는 allow가 기본이어야 한다. |
| 4-3 | 민감정보 외부 전송 금지 | 기본 설계는 로컬 Ollama만 사용한다. |
| 4-4 | JSON 응답 강제 | 모델 응답은 구조화 JSON으로 파싱되어야 한다. |
| 4-5 | 소스코드 수정 전 승인 필요 | 이 문서 검토 후 명시 승인 전까지 구현하지 않는다. |

## 5. 필요한 입력값

| 번호 | 입력 | 출처 |
|---|---|---|
| 5-1 | HTTP method/path/query/header/body_preview | `RequestContext` |
| 5-2 | 1차 룰 탐지 결과 | `Finding` 목록 |
| 5-3 | AI 설정값 | 환경 변수 |
| 5-4 | 모델 상태 | Ollama API 응답 |

## 6. 기대 출력값

| 번호 | 출력 | 설명 |
|---|---|---|
| 6-1 | AI 판단 결과 | 악성 여부, 신뢰도, 공격 유형, 심각도, 사유, 권장 조치 |
| 6-2 | WAF Finding | `AI-SECOND-PASS` 규칙 ID를 가진 표준 탐지 결과 |
| 6-3 | 상태 API 결과 | AI 활성화 여부, 모델명, 연결 상태, 최근 오류 |
| 6-4 | 대시보드 표시 | AI 차단/허용/실패 상태를 운영자가 확인 |

## 7. 애매한 부분과 임시 가정

| 번호 | 애매한 부분 | 임시 가정 | 확인 필요 여부 |
|---|---|---|---|
| A1 | 사용할 기본 모델 | `qwen2.5:7b-instruct`를 기본으로 유지 | 필요 |
| A2 | AI 판단을 로그에 어디까지 저장할지 | 신뢰도, 공격 유형, 요약 사유만 저장 | 필요 |
| A3 | AI allow 판단도 저장할지 | 운영 가시성을 위해 최근 상태에는 저장, 트래픽 이벤트에는 선택 저장 | 필요 |
| A4 | 외부 LLM 지원 여부 | 이번 완전구현 범위에서는 제외 | 필요 |
