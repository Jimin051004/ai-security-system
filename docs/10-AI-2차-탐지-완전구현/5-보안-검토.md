# 10-5. 보안 검토

## 1. 신뢰할 수 없는 입력

| 번호 | 입력 | 위험 |
|---|---|---|
| 1-1 | URL path/query | 공격자가 직접 제어 가능 |
| 1-2 | request body | 비밀번호, 토큰, 페이로드 포함 가능 |
| 1-3 | headers | Cookie, Authorization 포함 가능 |
| 1-4 | AI 모델 응답 | 비정상 JSON, 환각, 스키마 위반 가능 |

## 2. 인증 / 인가 고려사항

| 번호 | 항목 | 대응 |
|---|---|---|
| 2-1 | AI 상태 API | 워커 콘솔 API는 admin 세션 필요 |
| 2-2 | `/__proxy/health` | 공개 가능하므로 민감정보 제외 |
| 2-3 | 대시보드 | 기존 로그인 세션 기반 유지 |

## 3. 데이터 검증

| 번호 | 검증 대상 | 검증 방식 |
|---|---|---|
| 3-1 | confidence | 0.0~1.0 범위로 clamp |
| 3-2 | severity | enum에 없는 값은 기본값으로 정규화 |
| 3-3 | recommended_action | allow/block 외 값은 보수적으로 정규화 |
| 3-4 | raw response | dict가 아니면 실패 처리 |
| 3-5 | model timeout | 예외 처리 후 기존 정책 유지 |

## 4. 민감정보 처리

| 번호 | 항목 | 대응 |
|---|---|---|
| 4-1 | Authorization | `[REDACTED]` 처리 |
| 4-2 | Cookie | `[REDACTED]` 처리 |
| 4-3 | password/token/secret | 정규식 기반 마스킹 |
| 4-4 | body_preview | 최대 길이 제한 |
| 4-5 | evidence | 길이 제한 및 마스킹 |

## 5. 로그 처리

AI 로그에는 아래만 저장한다.

| 번호 | 저장 가능 | 저장 금지 |
|---|---|---|
| 5-1 | attack_type | 원본 Cookie |
| 5-2 | confidence | Authorization |
| 5-3 | reason 요약 | password/token 원문 |
| 5-4 | latency/error type | body 전체 원문 |

## 6. 가능한 취약점

| 번호 | 취약점 가능성 | 원인 | 대응 |
|---|---|---|---|
| 6-1 | 민감정보 노출 | 요청 원문을 모델/로그에 전달 | 마스킹, 길이 제한, 테스트 추가 |
| 6-2 | 프롬프트 인젝션 | 공격자가 body에 모델 지시문 삽입 | JSON 스키마 검증, 약한 근거 allow 원칙 |
| 6-3 | 오탐 차단 | AI가 정상 요청을 악성으로 판단 | confidence threshold, suspicious mode, 대시보드 검토 |
| 6-4 | 미탐 | 모델이 공격을 정상으로 판단 | 기존 룰 우선, AI는 보조로만 사용 |
| 6-5 | DoS | 모든 요청에 모델 호출 | suspicious mode, timeout, body 제한 |
| 6-6 | 모델 장애 | Ollama 미실행/timeout | 기존 룰 정책으로 fallback |

## 7. 보안 체크리스트

- [ ] 외부 입력 검증
- [ ] 민감정보 하드코딩 없음
- [ ] 인증 필요한 기능 확인
- [ ] 권한 검증 확인
- [ ] 에러 메시지에 민감정보 노출 없음
- [ ] 로그에 민감정보 저장 없음
- [ ] AI 요청 body 길이 제한
- [ ] AI 응답 JSON 스키마 검증
- [ ] 모델 실패 시 기존 WAF 정책 유지
- [ ] AI 판단은 보조 판단임을 UI와 문서에 명시

## 8. 발표용 보안 설명

AI 2차 판단은 기존 룰 기반 WAF를 대체하지 않는다. 기존 룰은 예측 가능하고 감사 가능한 1차 방어선이고, AI는 룰로 명확히 차단되지 않은 의심 요청을 설명 가능한 형태로 보조 판단하는 역할이다. 이 구조는 AI의 환각과 지연 문제를 줄이면서도, 운영자가 공격 의도를 이해하는 데 도움을 준다.
